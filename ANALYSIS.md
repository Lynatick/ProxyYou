## Hiddify: проверенные части кода

1. **Подписки:** `lib/features/profile/data/profile_repository.dart` содержит `upsertRemote`, обновление существующей подписки по URL, временный файл, проверку конфигурации и обновление БД. `profile_parser.dart` читает содержимое и метаданные подписки. `profile_notifier.dart` связывает операции с экраном и уведомлениями.
2. **Хранение:** `lib/core/db/db.dart` использует Drift/SQLite и миграции. На macOS каталог БД может быть общим каталогом Library, поэтому в производной версии изменено имя базы с `db` на `proxyyou_db`. Это предотвращает совпадение имён с установленным Hiddify; автоматический перенос его профилей не выполняется.
3. **Обновление:** `profiles_update_notifier.dart` запускает периодическую проверку раз в 15 минут, учитывает интервал профиля и последовательно обновляет подписки, чтобы не вызывать проверку и перезапуск общего ядра параллельно. Это механизм работающего приложения, а не гарантированный фоновый планировщик ОС.
4. **Соединение:** `connection_repository.dart` применяет настройки и передаёт путь конфигурации в `HiddifyCoreService.start/restart`. `connection_notifier.dart` управляет состояниями, переключением, восстановлением и повторным подключением при смене профиля.
5. **Android:** `VPNService.kt` реализует `VpnService`, защищает сокеты ядра с помощью `protect(fd)` и исключает собственный пакет из VPN, предотвращая петлю. Manifest описывает службу VPN и foreground service. Эти механизмы сохранены.
6. **macOS:** сохранены нативный Runner, сетевые entitlements и механизм Hiddify Core. Для проверки воспроизведения добавлен нативный WKWebView с принудительным HTTP CONNECT-прокси, без прямого выхода при ошибке.
7. **HTTP:** `dio_http_client.dart` имеет режимы `proxy`, `direct`, `both`. В `both` допускается DIRECT после локального прокси, что подходит для некоторых сценариев скачивания, но не доказывает доступ через прокси. Поэтому для YouTube добавлен отдельный клиент с единственным маршрутом `PROXY 127.0.0.1:<port>`.
8. **Сборка:** `pubspec.yaml` требует Flutter 3.38.5 / Dart 3.10.4. `dependencies.properties` указывает Hiddify Core 4.1.0. Сборка выявила расхождение: Kotlin-адаптер из выбранного commit ожидает более новые PlatformInterface/TunOptions, чем содержит выпущенный AAR 4.1.0. В ProxyYou адаптер приведён к фактическому API: одна DNS-строка, одно имя Android-пакета и отсутствие новых заглушек bridge/shell/neighbor/cancelNotification. Транспорт и парсинг протоколов делегированы этому ядру; их криптографическая реализация отдельно не аудировалась.

## Happ: границы анализа

[Публичный репозиторий](https://github.com/Happ-proxy/happ-desktop) заявляет Xray Core, правила маршрутизации и VLESS/Reality, VMess, Trojan, Shadowsocks и SOCKS. Дерево скачанного commit содержит README и материалы релизов. В нём нет исходников UI, службы VPN, парсера подписок или тестов. Поэтому сопоставлять внутренние алгоритмы Happ и Hiddify, оценивать безопасность реализации Happ или заявлять перенос его кода оснований нет.

## Выбранная реализация

ProxyYou — локальная производная версия Hiddify, а не независимо написанное прокси-ядро. Такой выбор сохраняет реальные нативные службы и разбор подписок. Основные изменения: собственный экран, отдельный идентификатор и БД, сетевой YouTube probe, нативные плееры для доказательства воспроизведения, тесты и сборка. Остальные механизмы унаследованы и не должны считаться заново полностью проверенными.

## YouTube: что означает результат

- `www.youtube.com/generate_204`: проверяется достижимость HTTPS-origin и точный пустой ответ 204.
- `i.ytimg.com`: проверяется публичная миниатюра, HTTP 200, Content-Type и начало JPEG.
- Редирект, HTTP 403/429/5xx, HTML вместо картинки, ошибка TLS, отказ прокси и тайм-аут не считаются успехом.
- На каждый запрос установлен общий предел времени 12 секунд и предел тела 256 КиБ. При смене соединения сокеты закрываются.
- Достижимость сервиса используется только как предварительный результат. Для успешной проверки требуется отдельное воспроизведение настоящего тестового видео в WKWebView / Android WebView.
- Общий JavaScript наблюдает минимум 5 секунд непрерывного продвижения времени и минимум 10 новых отображённых кадров. Реклама, перемотка, пауза, отсутствие кадров и смена источника не дают успеха.
- Нативная часть и Dart независимо проверяют идентификатор видео и пороги доказательства. Отложенный результат уничтоженной сессии не возвращает статус успеха.
- WebView направляет запросы страницы и видеопотока через локальный прокси ядра. Обход на уровне WebView запрещён; системное доверие TLS сохраняется.
- Запрос гарантированно проходит через локальный inbound ядра, но дальнейший путь зависит от правил ядра. Для доказательства конкретного удалённого узла нужно закрепить YouTube за этим outbound и проверить фактическую маршрутизацию.

## Следующие проверки перед использованием

Сборка обеих платформ, установка на Mac и Android, реальная подписка, проверка обновления во время соединения, смена сервера и режимов маршрутизации, отсутствие старых результатов после reconnect, доступ YouTube в браузере и реальное воспроизведение. URL подписок могут содержать токены; унаследованные диагностические логи нужно проверять перед передачей третьим лицам.

## macOS: права при подключении

На выбранном upstream обычный system-proxy запуск делегируется ядру, которое вызывает networksetup; локальная сборка не запрашивала необходимых прав. TUN также пытался создать интерфейс без привилегированного помощника. В версии 4.1.3 обычный системный прокси устанавливается через нативный SystemConfiguration с Authorization Services; ядро запускается без изменения системных настроек. TUN на macOS исключён из доступных режимов; полный туннель требует отдельной реализации Network Extension или привилегированного helper.
